## Idea pool (generated from pre-project sources + domain knowledge)

Each idea is tagged with its source: [brief] = from project brief, [scoping] = from scoping ideas, [constraints] = from constraints doc, [cross-project] = from mb-3-cs advisory knowledge, [agent] = generated by agent during ideation.

### Core concept ideas

1. **Three fixed intentions per day** [brief][scoping] — the user writes exactly three intentions each morning. Not adjustable. Forces prioritisation.
2. **Two-pass daily structure** [brief][scoping] — morning entry (set intentions), evening review (mark done/not-done). The day has two natural interaction points.
3. **Date-keyed records** [scoping] — each day is its own record, uniquely keyed by date. One record per day, no more, no less.
4. **Free-text intentions** [brief] — intentions are free text, not picked from a list. Personal, change daily, no categorisation.
5. **Optional reflection field** [scoping] — one-line reflection at evening review. "What shifted today?" Optional, not required.

### Discipline/honesty feature ideas

6. **Lock after midnight** [scoping] — once the day rolls over, the record is locked. Can't backfill or edit past days. Discipline feature, not technical.
7. **No backfilling** [scoping] — can't create records for past dates. If you didn't set intentions in the morning, there's no record for that day.
8. **No streaks** [scoping] — deliberately no streak counter. Streaks make you game the system. Honesty over score.
9. **No gamification** [brief][scoping] — no points, no badges, no achievements. The app is a discipline aid, not a game.

### UI/UX ideas

10. **Time-of-day detection** [scoping] — the app detects whether it's morning or evening and shows the appropriate view automatically.
11. **Notecard feel** [brief] — the morning entry should feel like writing on a notecard, not filling a form. Minimal, text-focused.
12. **History as scroll list** [brief][scoping] — past days shown as a simple scrollable list. Date, intentions, done/not-done. No charts, no filter, no search.
13. **Strikethrough for done** [scoping] — completed intentions shown with strikethrough in history. Visual, not data-driven.
14. **Mobile-first responsive** [constraints] — the app will be used on a phone. Responsive web, not native.
15. **Root URL redirects to Today** [scoping] — no home screen. Navigate to root → redirect to today's view.
16. **Locked day read-only** [scoping] — if a day is locked, show it read-only with a message: "This day is locked."

### Data model ideas

17. **Single table: `intentions`** [scoping] — date, three intention texts, three done flags, reflection, locked flag, timestamps. One table, eleven columns.
18. **Future-proof for users** [scoping][constraints] — structure data so adding a `user_id` column later doesn't require a rewrite. Soft constraint.
19. **Separate intentions table** [agent] — alternative to the single-table design: a `days` table + an `intentions` table (one-to-many). More normalised, but more complex. Open question for stage 10.
20. **Server-side lock logic** [scoping] — the lock-after-midnight logic should be server-side (Anvil Python), not client-side. Security: can't be bypassed by the client.

### Architecture/platform ideas

21. **Anvil Data Tables as the data layer** [constraints][cross-project] — use Anvil's built-in Data Tables, not an external database. Simpler, matches the platform. (Supported by mb-3-cs `docs/anvil-spec-table.md` section 4.)
22. **Anvil server-side Python for business logic** [scoping] — morning/evening detection, lock logic, date handling. Pure logic in server modules. (Supported by mb-3-cs `docs/architecture.md` — pure logic modules pattern.)
23. **Material Design 3 theme** [constraints][cross-project] — use Anvil's M3 theme dependency (4UK6WHQ6UX7AKELK). Same as mb-3-cs. (Supported by mb-3-cs `docs/ui-standards.md`.)
24. **CSS Overlay approach** [constraints][cross-project] — minimal custom CSS for spacing/typography. Don't override M3 component styling. (Supported by mb-3-cs `docs/design-direction.md`.)
25. **No external APIs** [constraints] — self-contained. No webhooks, no third-party services, no integrations.
26. **No authentication for v1** [constraints] — single user. No login, no RBAC. But data model doesn't break if auth is added later.
